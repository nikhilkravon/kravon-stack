## Flow 1 — Delivery/Pickup Order

### Entry Point

- **URL:** `http://localhost:8000?slug=<restaurant-slug>` (Orders frontend)
- **Product gate:** `requireFeature('has_orders')` in `server.js:207`

### Frontend Files Involved

| File | Role |
|------|------|
| `frontend/orders/assets/js/boot.js` | Async init: loads config, checks hours gate, initialises all modules |
| `frontend/orders/assets/js/cart.js` | Thin shim over shared `KravonCart.create()` |
| `frontend/shared/js/cart.js` | Shared cart engine: `KravonCart` factory |
| `frontend/orders/assets/js/modal.js` | Customization/add-ons modal |
| `frontend/orders/assets/js/renderer.js` | Renders menu, cart drawer, checkout summary |
| `frontend/orders/assets/js/checkout.js` | Order placement, Razorpay integration, confirmation screen |
| `frontend/orders/assets/js/behaviour.js` | Event delegation for all user interactions |
| `frontend/api-client/kravon-api.js` | HTTP client; `createOrder()`, `loadConfig()`, `submitReview()` |

### Cart Implementation

- **Object:** `window.OrdersCart` — a module wrapping a `KravonCart` instance
- **State storage:** In-memory JS array `_items[]` inside the closure. No localStorage, no sessionStorage. Cart is ephemeral — lost on page reload.
- **Config:** Reads delivery fees and GST rate from `window.CONFIG.orders` via `c.init()` on boot
- **Item shape:** `{ cartItemId, id (UUID), name, price, qty, note }`
- **Delivery fee:** Managed by `OrdersCart.setDeliveryFee()`, called when user selects standard/express delivery in checkout

### Customization Modal Flow

- `OrdersModal.init()` wires click handlers on menu items
- Items with `is_customizable: true` in `/config` response open the customization modal
- Customization selections are serialized into a `note` string on the cart item
- On modal "Add to cart", calls `OrdersCart.upsertItem(id, name, price, qty, note)`

### API Endpoint Sequence

```
1. GET /v1/restaurants/:slug/config?surface=orders
   → sets window.CONFIG (brand, menu categories, delivery fees, payment methods)

2. POST /v1/restaurants/:slug/orders
   Headers: Idempotency-Key: <crypto.randomUUID()>  ← generated by kravon-api.js:85
   Body (order_surface = 'orders'):
   {
     order_surface:     'orders',
     customer_name:     string,
     customer_phone:    string (digits only, stripped by checkout.js:97),
     delivery_address:  string,
     delivery_locality: string,
     delivery_landmark: string | undefined,
     special_notes:     string | undefined,
     delivery_type:     'standard' | 'express',
     payment_method:    'upi' | 'card' | 'cod',
     items: [{ id: UUID, name, price, qty, note? }]
   }

   Response (COD/offline):
   { ok: true, order: { id, total, razorpay_order_id: null, razorpay_key_id: null } }

   Response (Razorpay):
   { ok: true, order: { id, total, razorpay_order_id: 'order_xxx', razorpay_key_id: 'rzp_xxx' } }

3. [Razorpay path only] POST /v1/webhooks/razorpay
   → Razorpay sends payment.captured event
   → Backend verifies HMAC, confirms order in DB, emits order.created event

4. POST /v1/restaurants/:slug/reviews  (optional, post-order)
   Body: { order_id?, stars, feedback?, order_surface: 'orders' }
```

### Domain Service Call Chain

```
routes/orders.js:POST /
  → CreateOrderSchema.safeParse(req.body)           [Zod validation]
  → orderService.createOnlineOrder(req.tenant, data, idempotencyKey)
      → getClient()                                  [begin transaction]
      → repo.findByIdempotencyKey()                  [idempotency guard]
      → resolveMenuItems()                           [price verification vs DB]
      → calcGst(tenant, subtotal)                    [GST calculation]
      → customerService.findOrCreate()               [customer identity]
      → repo.insertOrder()                           [write orders.orders]
      → repo.insertOrderItems()                      [write orders.order_items]
      → razorpay.createPayment()                     [if needsRazorpay]
      → repo.updateOrderMetadata()                   [if Razorpay: store razorpay_order_id]
      → outbox.enqueue()                             [write platform.event_outbox INSIDE transaction]
      → COMMIT
      → events.emit('order.created', ...)            [immediate in-process delivery]
      → notifyService.orderConfirmed()               [if COD/offline: immediate WhatsApp + webhook]
```

### DB Writes

**Transaction 1 (atomic):**

| Table | Action | Key Values |
|-------|--------|-----------|
| `customer.customers` | INSERT or SELECT (findOrCreate) | `phone`, `name`, `tenant_id` |
| `orders.orders` | INSERT | `channel='web'`, `fulfillment_type='delivery'`, `status='pending'` (Razorpay) or `'confirmed'` (COD) |
| `orders.order_items` | INSERT (one row per item) | `menu_item_id`, `unit_price`, `quantity`, `total_price`, `addons_total` |
| `platform.event_outbox` | INSERT | `event_type='order.created'`, `payload=JSON` |

**Post-transaction (Razorpay webhook path):**

| Table | Action | Key Values |
|-------|--------|-----------|
| `orders.orders` | UPDATE | `status='confirmed'`, `metadata || { razorpay_payment_id }` |

### Events Emitted

1. `order.created` — emitted by `domains/ordering/service.js:200` (immediate) and by outbox poller (durable)
2. `order.status_updated` — emitted by `routes/orders.js:183` when staff patches status

### Outbox Entry

Created by `domains/ordering/outbox.js` inside the same transaction:
```
INSERT INTO platform.event_outbox (tenant_id, event_type, payload)
VALUES ($1, 'order.created', {tenantId, orderId, total, channel, isImmediateConfirm, ...})
```

Note: The v23 migration's `platform.event_outbox` schema diverges from the v20 schema definition. The v20 schema requires `aggregate_type TEXT NOT NULL` and `aggregate_id UUID NOT NULL`, but the v23 migration and `outbox.js` insert with only `(tenant_id, event_type, payload)`. The actual production table uses the v23 shape.

### Notifications Triggered

From `notification.listeners.js:registerAll()`:

| Event | In-App Notification | WhatsApp |
|-------|-------------------|----------|
| `order.created` | "New order received — Delivery order · ₹X.XX" | Kitchen WA + customer WA (delivery orders only) |
| `order.status_updated` | "Order status updated — Status changed to {status}" | None |

### Dashboard Propagation

- **View:** `dashboard/assets/js/views/orders.js` (`OrdersView`)
- **Mechanism:** Polling — `setInterval(() => _load(el), 10000)` — every 10 seconds
- **API endpoint:** `GET /v1/restaurants/:slug/orders?page=1&limit=25&status=<filter>`
- **New-order detection:** Compares `data.total` to `_lastCount`; if greater, increments `_newCount` and updates page title with count badge
- **Audio alert:** Optional; requires user gesture to unlock AudioContext

### Status Transition Sequence (Delivery)

```
pending       → customer submits Razorpay order (frontend does not transition yet)
                or: immediately 'confirmed' for COD/offline (set at INSERT time)

confirmed     → staff clicks "Confirm" in orders view → PATCH /orders/:id {status:'confirmed'}
                or: Razorpay webhook payment.captured → repo.confirmByRazorpayOrderId()

preparing     → staff clicks "Start Preparing" → PATCH /orders/:id {status:'preparing'}

ready         → staff clicks "Mark Ready" → PATCH /orders/:id {status:'ready'}

out_for_delivery → staff clicks "Out for Delivery" → PATCH /orders/:id {status:'out_for_delivery'}

completed     → staff clicks "Complete" → PATCH /orders/:id {status:'completed'}

cancelled     → staff clicks "Cancel" (with confirm dialog) → PATCH /orders/:id {status:'cancelled'}
```

Actor for all transitions after `confirmed`: staff only, via dashboard orders view.  
The `VALID_ORDER_STATUSES` array in `routes/orders.js:162` does not include `'pending'` — staff cannot revert an order to pending.

## Flow 2 — QR Dine-In Order

### Entry Point

- **URL:** `http://localhost:8000/tables/?slug=<slug>&table_id=<UUID>` (Tables frontend)
- **Product gate:** `requireFeature('has_tables')` in `server.js:229`
- **QR code** is generated by dashboard (`TablesView._showQr()`) and points to this URL

### QR Scan → Boot Sequence

```
1. GET /v1/restaurants/:slug/config?surface=dine_in
   → sets window.CONFIG (brand, menu categories)
   → checks CONFIG.hours.acceptsOrders gate

2. Parse ?table_id UUID from URL → window.TABLE_CONTEXT.tableId

3. GET /v1/restaurants/:slug/dine-in/boot?table_id=<UUID>
   → domains/dining/sessions.getStatus()    [check open session]
   → sessions.getSessionOrders()            [if open: fetch existing orders]
   Response: { ok, open: bool, session: { session_id, table_name, opened_at, ... }, orders: [] }

4. [If open=false] Show "Table not active" screen — order blocked.

5. _showGuestPopup() — modal collects guestName + guestPhone, stored in window.TABLE_CONTEXT
```

### Session Resolution Logic (`domains/dining/sessions.js:getStatus`)

```sql
SELECT s.id, s.opened_at, s.covers, s.session_status,
       s.bill_owner_name, s.bill_requested_at, t.name AS table_name
FROM dining.sessions s
JOIN dining.tables t ON t.id = s.table_id
WHERE s.table_id = $1 AND s.tenant_id = $2
  AND s.closed_at IS NULL AND s.deleted_at IS NULL
LIMIT 1
```

A session must be explicitly opened by staff (`POST /dine-in/session/open`, JWT required) before customers can order. Without an open session, the entire flow blocks.

### Menu Render

Same as delivery: menu data comes from `/config`, rendered by `initTablesRenderer()`. Categories structure identical.

### Cart (Tables)

- **Object:** `window.TablesCart` — thin shim over `KravonCart.create()`
- **Key difference from orders cart:** Configured with `c.configure({ minOrder:0, deliveryStandard:0, freeDeliveryAt: Infinity, gstRate:0 })` — no delivery fees, no GST calculation in cart
- **GST for dine-in orders:** Not calculated on the frontend; backend dine-in order path (`repo.insertDineInOrder`) sets `tax_amount=0`

### Order Creation (QR Dine-In)

```
POST /v1/restaurants/:slug/dine-in/order
Body:
{
  session_id:   UUID,
  guest_name:   string (optional),
  guest_phone:  string (optional),
  items: [{ menu_item_id: UUID, quantity: int, customizations?: string }],
  special_notes?: string
}
Response: { ok: true, order_id: UUID, total: number }
```

Note: This uses a **different route and payload shape** than delivery orders. Items use `menu_item_id` (not `id`) and `quantity` (not `qty`). There are no addons in the dine-in item schema.

### Domain Service Call Chain (Dine-In)

```
routes/dine-in.js:POST /order
  → DineInOrderSchema.safeParse(req.body)
  → orderService.createDineInOrder(req.tenant, { sessionId, guestName, guestPhone, items, specialNotes })
      → getClient()
      → SELECT dining.sessions WHERE id=$1 AND closed_at IS NULL    [session open check]
      → customerService.findOrCreate()                               [identity, if phone provided]
      → UPDATE dining.sessions SET bill_owner_name/phone             [if first scanner with identity]
      → SELECT menu.menu_items WHERE id = ANY(itemIds)               [price lookup]
      → repo.insertDineInOrder()                                     [write orders.orders]
      → repo.insertDineInOrderItems()                                [write orders.order_items]
      → COMMIT
      → events.emit('dine_in.order_created', ...)
```

### Key Differences vs Delivery Order

| Aspect | Delivery | Dine-In |
|--------|----------|---------|
| Route | `POST /orders` | `POST /dine-in/order` |
| Channel | `web` | `qr` |
| Fulfillment | `delivery` | `dine_in` |
| Initial status | `pending` (Razorpay) or `confirmed` (COD) | Always `confirmed` |
| Session ID | `NULL` | Set to active session UUID |
| Customer ID | Set via findOrCreate | Not set (no FK written in `insertDineInOrder`) |
| Idempotency | Header-based with DB unique index | None |
| GST | Calculated and stored in metadata | `tax_amount=0`, no GST snapshot |
| Delivery fee | Possible | 0 |
| Outbox event | Yes (`order.created`) | No outbox entry |
| Payment | Can be Razorpay or COD | No payment captured; always immediate |

### Kitchen View Propagation

- **GET /dine-in/kitchen** (JWT required) → `kitchen.getKitchenView()`
- Returns two sections:
  - `tables[]`: open sessions with orders in `status IN ('pending', 'confirmed', 'preparing')`
  - `queue[]`: delivery/pickup orders with `session_id IS NULL` and same status filter
- Dashboard `KitchenView` polls every 10 seconds (`setInterval(() => _load(el), 10000)`)
- Kitchen staff see action buttons: "Start Preparing" (confirmed→preparing) and "Mark Ready" (preparing→ready)
- Both kitchen actions call `PATCH /orders/:id` which goes through `orderService.updateStatus()` and emits `order.status_updated`

### Bill Request Flow

```
Customer: [Request Bill button in tables frontend]
  → KravonAPI.requestDineInBill(sessionId, guestName)
  → POST /dine-in/session/request-bill
     Body: { session_id: UUID, requested_by?: string }
  → sessions.requestBill()
     UPDATE dining.sessions
       SET session_status = 'bill_requested',
           bill_requested_at = COALESCE(bill_requested_at, NOW()),
           bill_requested_by = COALESCE(bill_requested_by, $3)
       WHERE id = $1 AND closed_at IS NULL
  → events.emit('dine_in.bill_requested', { tenantId, sessionId, requestedBy })
     [No listener registered for dine_in.bill_requested — no in-app notification created]
```

### Session Close

```
Staff: [Close session button in dashboard tables view]
  → POST /dine-in/session/close
     Body: { session_id: UUID }
  → sessions.closeSession()
     1. SELECT SUM(total_amount) FROM orders.orders WHERE session_id=$1 AND status NOT IN ('cancelled','refunded')
     2. UPDATE dining.sessions SET closed_at=NOW(), total_billed=$1 WHERE id=$2 AND closed_at IS NULL
     3. UPDATE dining.tables SET status='available' WHERE id=$1
     4. COMMIT
     5. events.emit('session.closed', { tenantId, sessionId, tableId, totalBilled })
```

### Bill Generation

- **GET /dine-in/bill?session_id=UUID** (JWT required) → `sessions.getBill()`
- Aggregates all non-cancelled orders for the session with a lateral join to their items
- Calculates: `subtotal`, `taxable_amount`, `cgst_amount`, `sgst_amount`, `total_tax`, `grand_total`
- GST consistency check: warns if GST rates differ across orders in the same session (`gst_inconsistent: true`)
- Dashboard `TablesView._showBill()` renders a modal with print support
- **Gap:** No dedicated printable bill endpoint — the dashboard inlines the HTML for `window.print()`. No customer-facing bill URL exists.

## Flow 3 — Catering Lead

### Lead Capture Form

- **URL:** `http://localhost:8000/<slug>/catering/?slug=<slug>` (Catering frontend)
- **Product gate:** `requireFeature('has_catering')` in `server.js:214`
- **Boot sequence:** `catering/boot.js` → `KravonAPI.loadConfig('catering')` → `initRenderer()` → `initBehaviour()`
- **Form fields:** Name, Company (required); Email, Phone (required); Budget (radio), Headcount/pax (radio), Event type (radio); Date range (optional); Notes (optional)

### Client-Side Scoring

`catering/behaviour.js:scoreLead()` computes a score client-side for display only:

| Factor | Values | Points |
|--------|--------|--------|
| Budget | `below-1L`=0, `1-2.5L`=2, `2.5-5L`=3, `5L+`=4 |
| Pax | `50-150`=1, `150-300`=2, `300-500`=3, `500+`=3 |
| Type | `daily-office`=3, `conference`=3, `corporate-offsite`=2, `product-launch`=2, `other`=1 |

**Discrepancy:** Frontend `TYPE_SCORES` maps `daily-office:3, conference:3` while backend `catering/service.js:TYPE_SCORES` maps `corporate-offsite:3, product-launch:3, conference:2, daily-office:2`. Frontend scores display-only; the canonical score stored in DB comes from the backend.

### API Call

```
POST /v1/restaurants/:slug/leads
Body:
{
  name:       string,
  company:    string,
  email:      string,
  phone:      string,
  budget?:    '5L+' | '2.5-5L' | '1-2.5L' | 'below-1L',
  headcount?: '500+' | '300-500' | '150-300' | '50-150',
  event_type?: string,
  date_start?: 'YYYY-MM-DD',
  date_end?:   'YYYY-MM-DD',
  notes?:      string
}
Response: { ok: true, lead: { ref: 'RTR-XXXXX' } }
```

The response only returns `ref` — the `tier` is not in the HTTP response. The frontend gets `tier` from the `result.lead` object. Looking at `catering/service.js:71`, `createLead` returns `{ id, ref, tier }` and `routes/leads.js:37` returns `{ ok: true, lead: { ref: result.ref } }` — **the `tier` is missing from the HTTP response**. The frontend `behaviour.js:184` accesses `result.lead.tier` which will be `undefined`.

### Backend Lead Processing (`domains/catering/service.js:createLead`)

```
1. scoreLead(budget, headcount, event_type)  → numeric score
2. scoreTier(score)                          → 'hot' | 'warm' | 'cool'
3. generateRef(tenant.name)                  → 'RTR-XXXXXXXX' (base36 timestamp)
4. INSERT INTO catering.leads (
     tenant_id, contact_name, contact_phone, contact_email,
     event_type, preferred_date_from, preferred_date_to,
     notes, source='web', status='new',
     custom_fields={ company, budget, headcount, ref, score, tier }
   )
5. notifyService.leadReceived(tenant, lead)  → fire-and-forget WA + webhook
```

**Note:** `budget_min`, `budget_max`, `guest_count_min`, `guest_count_max` columns exist in the schema but are not populated. The string values (`budget`, `headcount`) are stored in `custom_fields` JSONB instead.

### Events After Lead Creation

- `events.emit('lead.created', { tenantId, leadId, contactName, eventType })` — emitted in `routes/leads.js:35`
- No outbox entry for leads (no durable delivery guarantee)

### Dashboard Pipeline View (`CateringView`)

- **View file:** `dashboard/assets/js/views/catering.js`
- **API endpoint:** `GET /v1/restaurants/:slug/leads?page=1&limit=25&status=<filter>`
- **No polling** — `CateringView` has no `setInterval`. Data loads once on view init, refreshed only on tab switch or action button click.
- **Pipeline stages (ordered):** new → contacted → proposal_sent → negotiating → confirmed → lost
- Staff can advance or reject leads. Advance calls `PATCH /leads/:id { status: <next> }`

### Status Transitions (Leads)

```
new          → staff marks Contacted     → PATCH /leads/:id { status: 'contacted' }
contacted    → staff sends Quote         → PATCH /leads/:id { status: 'proposal_sent' }
proposal_sent→ staff marks Negotiating   → PATCH /leads/:id { status: 'negotiating' }
negotiating  → staff clicks Confirm      → PATCH /leads/:id { status: 'confirmed' }
any          → staff clicks Reject       → PATCH /leads/:id { status: 'lost' }
```

On `status='confirmed'`:
- `updateLeadStatus()` calls `createCateringEventFromLead()` which inserts into `catering.events`
- `events.emit('lead.status_updated', { status: 'confirmed', ... })` triggers `notification.listeners.js:lead.status_updated` which calls `notify.reviewRequest()` — sends a WhatsApp review request to the lead's `contact_phone`
- `events.emit('lead.converted', { tenantId, leadId })` → in-app "Catering lead converted" notification

### Does a Catering Lead Create an `orders.orders` Record?

**No.** Catering leads live entirely in `catering.leads` and `catering.events`. No record is written to `orders.orders` at any point in the catering flow. Revenue from catering is not tracked in the orders schema.

## PostgreSQL Truth Map

### `orders.orders` — Complete Column Documentation

| Column | Type | Values | Set By | Notes |
|--------|------|--------|--------|-------|
| `id` | UUID | gen_random_uuid() | DB default | Primary key |
| `tenant_id` | UUID | — | `repo.insertOrder()` / `insertDineInOrder()` | Not nullable |
| `location_id` | UUID | NULL | Never set in any current code path | Reserved; not used |
| `customer_id` | UUID | NULL or FK | `customerService.findOrCreate()` | NULL for dine-in orders (insertDineInOrder doesn't set it) |

### `orders.orders.subtotal_amount`, `delivery_charge`, `tax_amount`, `total_amount` — Calculation Source

**Online delivery (`createOnlineOrder`):**
```
subtotal     = Σ (item.price × item.qty) + Σ (addon.price × item.qty)
deliveryFee  = delivery_type='express' ? stdFee×2
             : subtotal >= freeAt ? 0 : stdFee
             (stdFee from tenant.free_delivery_above / delivery_fee settings)
taxAmount    = gstEnabled ? calcGst(tenant, subtotal).taxAmount : 0
total        = gstSnapshot && !tenant.gst.inclusive
             ? subtotal + deliveryFee + taxAmount
             : subtotal + deliveryFee
```

**QR Dine-In (`createDineInOrder`):**
```
subtotal     = Σ (db_price × quantity)
taxAmount    = 0  (hardcoded)
total        = subtotal
```

### `idempotency_key`

Set by `kravon-api.js:85` (`crypto.randomUUID()`) on every `createOrder()` call. Passed as `Idempotency-Key` HTTP header, read by `routes/orders.js:105` (`req.headers['idempotency-key']`). Only checked and enforced for `createOnlineOrder()`; `createDineInOrder()` has no idempotency protection.

### Outbox Poller Details

- **File:** `services/outbox.poller.js`
- **Interval:** 5 seconds (`POLL_INTERVAL_MS = 5000`)
- **Batch size:** 50 events per poll
- **Query:** `SELECT ... WHERE status IN ('pending','failed') AND next_attempt_at <= NOW() ... FOR UPDATE SKIP LOCKED`
- **Retry schedule:** 0s → 30s → 2m → 10m → 1h → dead after 5 attempts
- **Action:** Re-emits via `events.emit(row.event_type, { ...row.payload, _outboxId })` → same listeners fire again
- **Note:** Only `order.created` events currently use the outbox. The `_outboxId` field in the payload is an internal marker for deduplication purposes but no deduplication is currently implemented in the listeners.

## Gaps and Inconsistencies

### G01 — `dine_in.bill_requested` event has no in-app notification listener

**File:** `services/notification.listeners.js`  
**What:** `sessions.requestBill()` emits `dine_in.bill_requested` at `sessions.js:212`, but there is no `events.on('dine_in.bill_requested', ...)` registered in `notification.listeners.js`. When a customer requests the bill, no in-app notification reaches the staff dashboard bell feed.  
**Impact:** Staff have no real-time alert when a customer clicks "Request Bill". They must watch the kitchen view or tables view, both of which poll every 10–15 seconds. The `bill_requested_at` flag is visible in both views once polled, but no push occurs.

### G02 — `tier` missing from catering lead API response

**File:** `api/routes/leads.js:37`  
**What:** `routes/leads.js` returns `{ ok: true, lead: { ref: result.ref } }`. The service returns `{ id, ref, tier }` but only `ref` is forwarded. The catering frontend `behaviour.js:184` accesses `result.lead.tier` which resolves as `undefined`.  
**Impact:** Tier badge on the confirmation screen shows blank or incorrect value. The correct tier is stored in DB (`custom_fields.tier`); it just isn't surfaced to the frontend.

### G03 — QR dine-in orders have no idempotency protection

**File:** `domains/ordering/service.js:createDineInOrder`  
**What:** `createDineInOrder()` has no idempotency key check. Double-taps or network retries on the "Place Order" button can create duplicate orders in the same session.  
**Impact:** Duplicate orders appear in the kitchen view. No deduplication mechanism exists.

### G04 — `customer_id` is NULL for all QR dine-in orders

**File:** `domains/ordering/repository.js:insertDineInOrder` (line 53–63)  
**What:** `insertDineInOrder()` does not pass `customer_id` to the INSERT. The `customerService.findOrCreate()` is called (to record the identity) but the returned customer ID is discarded. The `orders.orders` row has `customer_id = NULL`.  
**Impact:** QR dine-in orders are invisible in customer order history. The `customers` list's `order_count` and `total_spend` cannot include dine-in spend. CRM is incomplete for dine-in customers.

### G05 — `fulfillment_type='pickup'` is an enum value but no code path creates pickup orders

**Files:** `kravon_schema_v20.sql`, `domains/ordering/service.js:150`  
**What:** `createOnlineOrder()` sets `fulfillmentType = data.order_surface === 'tables' ? 'dine_in' : 'delivery'`. There is no branch for `pickup`. The `STATUS_NEXT_PICKUP` state machine in `orders.js:view` references it, but it can never be reached.  
**Impact:** The "Pickup" fulfillment type is dead code. Orders frontend has no pickup mode.

### G06 — `PATCH /settings/restaurant` and `PATCH /settings/notifications` do not call `bustConfigCache`

**File:** `api/routes/settings.js` (not audited directly, noted in CLAUDE.md Known Gap #8)  
**What:** When restaurant settings are updated (e.g., delivery fee, GST rate), the in-memory config cache is not invalidated. All subsequent `/config` requests return stale data for up to 60 seconds.  
**Impact:** Operators changing delivery fees or GST settings see no immediate effect. Orders placed during the 60s window use old pricing.

### G07 — Outbox `platform.event_outbox` schema mismatch between v20 and v23

**Files:** `db/kravon_schema_v20.sql:1936`, `db/migrations/v23-order-idempotency.js:31`  
**What:** v20 schema defines `event_outbox` with columns `aggregate_type TEXT NOT NULL`, `aggregate_id UUID NOT NULL`, `retry_count SMALLINT`, `error_detail TEXT`, `processed_at TIMESTAMPTZ`. v23 migration creates a different schema: `attempts INT`, `last_error TEXT`, `delivered_at TIMESTAMPTZ`, `next_attempt_at TIMESTAMPTZ`. The `outbox.js` INSERT uses `(tenant_id, event_type, payload)` — 3 columns — which would fail against the v20 schema (aggregate_type NOT NULL). Production runs on the v23 schema.  
**Impact:** v20 schema cannot be applied fresh without v23 running immediately after. New deployment documentation should note that v23 must be applied before any dine-in orders.

### G08 — Catering pipeline has no polling; stale view for active users

**File:** `dashboard/assets/js/views/catering.js`  
**What:** `CateringView.init()` has no `setInterval`. The leads list is fetched once on init and only refreshes when a tab is clicked or an action button is used.  
**Impact:** If two staff members are managing leads simultaneously, their views diverge silently. No new-lead notification appears in the catering view (contrast with orders view's `+N new` badge).

### G09 — Score mismatch between frontend and backend

**Files:** `frontend/catering/assets/js/behaviour.js:109`, `domains/catering/service.js:24`  
**What:** Frontend and backend use different scoring tables for event type:
- Frontend: `daily-office:3, conference:3, corporate-offsite:2, product-launch:2`
- Backend: `corporate-offsite:3, product-launch:3, conference:2, daily-office:2`  
**Impact:** The tier displayed on the confirmation screen may differ from the tier stored in DB. Staff-facing CRM shows correct (backend) tier; customer confirmation screen may show wrong tier.

### G10 — No outbox entry for dine-in orders

**File:** `domains/ordering/service.js:createDineInOrder`  
**What:** `createDineInOrder()` commits the transaction and then calls `events.emit('dine_in.order_created', ...)` directly without writing an outbox entry first. If the process crashes between `COMMIT` and `events.emit`, the notification is lost.  
**Impact:** In the event of a process crash immediately after a dine-in order is committed, the kitchen in-app notification for that order is permanently lost. The order itself is safe (committed), but staff may not see it in the bell feed.

### G11 — `reservation_id` FK missing from `dining.sessions` schema

**Files:** `db/kravon_schema_v20.sql:1412`, `domains/dining/sessions.js:43`  
**What:** The v20 schema `dining.sessions` definition does not declare a FK for `reservation_id` even though `sessions.openSession()` writes `reservation_id` and `openSession` references it. The column exists (set by the service) but no FK constraint enforces referential integrity.  
**Impact:** Orphaned `reservation_id` values in sessions are possible if a reservation is deleted.

### G12 — Catering `CateringView` displays `lead.budget_min`, `lead.guest_count_min` but these are always NULL

**File:** `dashboard/assets/js/views/catering.js:151`  
**What:** The detail row in `CateringView` tries to render `lead.budget_min`, `lead.budget_max`, `lead.guest_count_min`, `lead.guest_count_max`. These DB columns exist in the schema but `createLead()` never populates them — the string values go into `custom_fields.budget` and `custom_fields.headcount` instead.  
**Impact:** Budget and headcount fields in the lead detail panel always show as blank/absent on the dashboard, even when the customer submitted them.

## Single Source of Truth Assessment

### Is `orders.orders` the Canonical Order Record?

**Yes, `orders.orders` is the single canonical order record for all transactional flows.** Every order — whether delivery, dine-in, or takeaway — results in exactly one row in `orders.orders` and one or more rows in `orders.order_items`. All status transitions are written to `orders.orders.status`. All financial totals are stored in `orders.orders`.

### Secondary Tables That Hold Order-Related State

| Table | Schema | Purpose | Relationship to `orders.orders` |
|-------|--------|---------|--------------------------------|
| `orders.order_items` | `orders` | Line items for every order | FK `order_id → orders.orders.id`. Required for full order detail. |
| `dining.sessions` | `dining` | Groups dine-in orders; tracks bill lifecycle | `orders.orders.session_id → dining.sessions.id`. A session is a container — the orders are the commerce records. |
| `dining.tables` | `dining` | Physical table status (`available`/`occupied`/etc) | Indirect: tables have sessions; sessions have orders |
| `dining.reservations` | `dining` | Pre-arrival bookings | Indirect via `sessions.reservation_id`. No direct link to `orders.orders`. |
| `customer.customers` | `customer` | Customer identity; resolved at order creation | `orders.orders.customer_id → customer.customers.id` (NULL for dine-in) |
| `platform.event_outbox` | `platform` | Durable event delivery buffer | Contains `order.created` payload. Transient — rows are marked `delivered` after processing. |
| `notifications.notifications` | `notifications` | In-app bell feed entries | `entity_id = order.id` for order-related notifications. Supplementary UI state, not order state. |
| `catering.leads` | `catering` | Catering enquiries and pipeline | **Independent of `orders.orders`**. Catering revenue is not captured in the orders system. |
| `catering.events` | `catering` | Confirmed catering event records | Created from a confirmed lead. Not linked to `orders.orders`. |

### State That Is Fragmented

1. **Customer identity for dine-in:** `orders.orders.customer_id` is NULL for all QR dine-in orders. Guest identity is only in `orders.orders.metadata.guest_name / guest_phone`. Cross-order customer tracking is broken for dine-in.

2. **Delivery address:** Stored in `metadata.delivery_address` / `metadata.delivery_locality` / `metadata.delivery_landmark` rather than the `delivery_address_id` FK column. The `customer.addresses` table and the FK column exist but are unused.

3. **Catering revenue:** Exists only in `catering.leads.custom_fields.budget` (a text range string, e.g. `'5L+'`). No confirmed catering amount flows into `orders.orders`. The insights dashboard cannot report catering revenue.

4. **Payment method:** Stored in `metadata.payment_method` as a string, not in a `payments.payments` row. The `payments` schema exists and has a `payment_status` ENUM but the payment layer is entirely bypassed for current order flows. Razorpay payment ID is stored as `metadata.razorpay_payment_id`.

### Conclusion

For the current three active flows (delivery, QR dine-in, takeaway), `orders.orders` is the unambiguous single source of truth for order existence, status, and financials. The fragmentation points listed above are gaps in the implementation rather than architectural alternatives — they represent columns or tables that are defined but not yet wired.
